# Red-team read: Claude Brain after a year of daily use (contract h-20261110-94bf6b)

Premise: it is November 2027 and the brain turned out harmful or useless to its owner. This read names the failure modes most likely to have caused that, ranked by likelihood times cost. Each one gives the mechanism, the file and line that shows it, the earliest signal, a severity and the cheapest fix or test. Read-only: nothing in the repository was changed.

Labels: **[verified]** means I read the code path or file that shows it. **[unconfirmed]** means the mechanism follows from the code but I did not reproduce it (I had no shell in this run).

---

## F1. The learning loop silently starves or jams on git. Severity: blocking (for "it learns")

**Mechanism.** Getting one session's lesson into memory takes eight hand-offs, and each can drop it. The model must (1) run `close`, (2) commit the inbox file in the brain repo, (3) push, and (4) open a PR. The owner must (5) merge it on his phone. Someone must (6) ask for "Consolidate". Its delta needs (7) another PR and (8) another merge. Consolidation only sees what has reached `main` (`.claude/skills/brain-learn/SKILL.md:16`). The weekly run is not scheduled (`NEEDS_YOU.md` item 6 is unresolved), and merges are manual (item 4 = B).
- Each cloud session gets its own branch: this one is `claude/nice-hopper-ko5975` (`.git/HEAD`) and the build session's was `claude/wizardly-darwin-91m4pl`. So "open or update one pull request" in practice means a new PR every session, roughly 300 a year. [verified: branch names]
- The Stop hook only writes the inbox file. It never commits or pushes (`.claude/hooks/session_end.py:38`). In two-repo sessions hooks do not load at all (`docs/EXECUTION_PLAN.md:40`). A session that ends before the model commits loses its record when the container goes. [verified]
- Parallel branches collide. Radar leads go to a file named by date that every session shares (`engine/radar.py:437`: `learning/inbox/<date>-radar.jsonl`; 22 leads on day one). Each consolidation appends to `learning/manifest.jsonl` and rewrites `stats/ml.json` and `learning/CHANGELOG.md`. There is no `.gitattributes` with `merge=union`. Two PRs from the same day, or two consolidations, therefore conflict at the end of the same files. A phone-only owner cannot resolve that. [verified: paths and no .gitattributes; conflict itself unconfirmed]
- A consolidation run on a branch cut before an earlier consolidation PR merged treats the same inbox files as pending, because "handled" comes from that branch's manifest (`engine/learn.py:1356`, `consumed_inbox`). Two deltas then consume the same records, and the second PR conflicts in `stats/ml.json`. [unconfirmed]

**Earliest signal.** Two weeks in: the number of inbox files on `origin/main` is well below the number of sessions, open PRs titled "learning inbox" pile up, and `brain ml report` still shows n < 8 per arm. The bandit then never acts (`EXECUTION_PLAN.md:91`). Today's evidence: one delta in the manifest, folding 2 records.

**Cheapest test (about 10 minutes).** In a scratch clone, cut branches A and B from `main`. On each, write one session inbox file plus one radar lead under today's date, then run `brain learn consolidate`. Merge A into `main`, then B. Expected: conflicts in `learning/inbox/<date>-radar.jsonl`, `learning/manifest.jsonl` and `stats/ml.json`. If B merges cleanly, downgrade this item.

**Cheapest fix.** `close` writes, commits and pushes the inbox file itself, as one command and not a model step. Radar files are named by session, not date. Add `.gitattributes` `merge=union` for `learning/inbox/*` and `learning/manifest.jsonl`. Consolidate only on `main` (the scheduled run), never on session branches.

## F2. A model-written rule can become a permanent "owner-stated" rule that the owner cannot remove. Severity: should-fix, close to blocking for harm

**Mechanism.** `learn note --trust owner-stated --quote Q --text T` checks only that Q, at least 12 characters, appears somewhere in a turn the owner typed (`engine/learn.py:353-366`, `MIN_QUOTE = 12` at line 83). Nothing checks that T says what Q says (`build_note`, `engine/learn.py:1382-1422`). Pasted text also counts as "typed": an email, an error message or a web page the owner pastes is a `user` string turn (`owner_turns`, lines 327-350).

Once consolidated, such an item:
- goes straight to `active` (`engine/learn.py:922-923`);
- is never demoted by harm (line 920, `not owner and x >= 3`);
- never decays (line 1171);
- cannot be superseded by any op (lines 724-725: "only the owner can replace it", but no op or command lets him);
- gets the top recall multiplier (I-08).

An owner correction against it, `learn correction --item <id>`, only becomes `INC_HARMFUL` (lines 1118-1120), and that cannot demote an owner-stated item. The only removal is a hand-written delta with `SET_STATUS retired` passed to `learn apply`, which no skill describes. Preferences that change during the year ("no tests this time", "use Vercel") become global and permanent. 12 owner-stated items already exist in `owner/standing.jsonl`. [verified: code paths]

**Earliest signal.** An owner-stated item whose text shares few content words with any owner turn. Or the owner saying "I never said that" or "not any more".

**Cheapest test.** In a session, run `learn note --trust owner-stated --quote "<any 12 characters he typed, e.g. 'yes go ahead'>" --text "Never write tests for small tools" --class software --evidence ...`, then `consolidate`. Expect it to be active. Then run `learn correction --kind quality --item <id> --quote ...` and `consolidate`, and expect it to stay active.

**Cheapest fix.** Require T's content words to be mostly contained in Q, or store Q as the text. Make an owner correction on an owner-stated item retire it, which is the owner overriding himself.

## F3. For a year, every enforcement is on the honour system. Severity: should-fix

**Mechanism.**
- GitHub checks have never run (`NEEDS_YOU.md` item 7), so branch protection (item 2) cannot be switched on.
- The guard hook does not load in two-repo sessions (`EXECUTION_PLAN.md:40`, `NEEDS_YOU.md` item 5), and it fails open by design (`.claude/hooks/guard_paths.py:35`).
- `learn verify` turns every mismatch into a warning while the zone is unlocked (`engine/learn.py:1369-1373`). The lock waits for "after the live checks" (D-08), and CB-101 to CB-112 have no date.
- So I-06 and rule 8 ("never edits brain files by hand") rest only on the model obeying `CLAUDE.md` and on an owner who reads diffs on a phone.
- A red cross on every push also teaches the owner to ignore red crosses. [verified: files; the alarm fatigue is a prediction]

**Earliest signal.** Visible now: `learn verify` prints "bootstrap period … warnings only", and every push shows a red X.

**Cheapest fix.** Set a date or a session count for the lock, not "after live checks". Until CI runs, make `boot` print one line saying "GitHub checks not running". Make `learn verify` warnings print in `doctor`.

## F4. "Done" in the requirements ledger goes stale and accepts free text. Severity: should-fix

**Mechanism.**
- `req verify` skips lines already `done` (`engine/req.py:187`). A requirement passed in March and broken in June stays done, and `req check` passes.
- `req evidence <id> "<any string>" --done` marks done with no check that the path, log or screenshot exists (`engine/req.py:151-172`).
- `req add --quote` is not checked against owner turns (`engine/req.py:107-130`), unlike `learn note --quote`. Paraphrased or missing sentences pass.
- The check command is written by the model, so `--check true` passes.

Rule 1 ("evidence before claims") then reports done on things that are not done. This is the exact failure the ledger exists to stop. Release gates catch regressions only where the gate covers them. [verified: code]

**Earliest signal.** A `STATUS.md` "done" line whose check exits non-zero when re-run by hand.

**Cheapest test.** In a scratch project: `req add --check "test -f x"`, `touch x`, `req verify` (done), `rm x`, `req verify`, `req check`. Expect it to stay done and `req check` to exit 0.

**Cheapest fix.** `req verify --all` re-runs done lines that have a check, and `req check` and `release` call it. Make `req evidence --done` require a path that resolves, or an `http(s)` URL.

## F5. A process tax with no measured benefit; headline numbers come from tuning sets. Severity: should-fix (measure before claiming)

**Mechanism.** A size-2 request runs boot, one `req add` per dictated sentence, plan, hire, settle, checkpoint and push, `req verify`, release, close, and the inbox commit and PR. Nobody has measured the cost against working without the brain: CB-109 is open, and `BUILD_STATUS.md` makes "no efficiency claim".

The only paired test of an added brain mechanism made things worse: templates lost 2 to 6 (`BUILD_STATUS.md:206`). The HR selector's 78% top-1 fell to 46% on a set written fresh. Recall's 0.781 recall@5 and routing's 107/107 are measured on sets they were tuned on (`docs/research/round2/04-retrieval.md:6,17`; `docs/REQUIREMENTS.md:18`: "the rules were tuned on most of it"). That is the same pattern that overstated HR by about 30 points. About a quarter of the owner's requests are in Spanish, while recall uses the English Porter stemmer (`engine/recall.py:162`). [verified: numbers as recorded; the recall overstatement is unconfirmed]

**Earliest signal.** Lead tokens per finished item in `brain ledger` higher on small projects than an unmanaged session doing the same work. Or recall returning nothing or the wrong item for Spanish queries.

**Cheapest test.** CB-109 with 8 pre-registered paired tasks (I-16). Plus a fresh, blind 30-query recall set, a third of it in Spanish, scored once.

## F6. Survivorship bias in what the brain learns. Severity: should-fix [unconfirmed]

**Mechanism.** The sessions that end abruptly are the failures, the long compactions and the usage-limit hits, and those are the ones that never run `close` or push. In cloud containers the transcript is gone by the next boot. `repair_unclosed` then records only an `unrecorded` ledger gap with no outcome (`engine/ledger.py:452-458`), and the open-session marker exists only if a checkpoint pushed it. So `mlearn` folds a set of outcomes skewed towards passes. Cheaper arms look safer than they are, calibration runs low, and drift alarms miss.

**Earliest signal.** The share of `unrecorded: true` ledger rows, together with a first-pass rate in `ml report` well above what the owner sees.

**Cheapest fix.** Write an `outcome: failed, provisional` record at `boot` and overwrite it at `close`, so the default is a failure, not silence.

## F7. Radar noise and inbox growth. Severity: minor

22 leads on the first day (`learning/inbox/2026-11-10-radar.jsonl`) is about 8,000 a year. Leads are confirmed only when a model follows the brain-learn skill. `boot` spends up to 4 s and 2 lines on news (`engine/detect.py:208-210`). Expected result: the owner and the model learn to skip the "news:" lines, and the official changes they were meant to catch, such as a model price or an id, are missed. Fix: count leads in `boot` and do not list them, and expire unconfirmed leads after 30 days.

## What would change the call

- **F1 drops to minor if:** the two-branch merge test above merges cleanly; or the owner picks auto-merge (item 4 = A) and CI runs (item 7) and the weekly consolidation runs on `main`; or a month of use shows inbox files on `main` at 90% or more of sessions.
- **F2 drops to minor if:** a sample of real owner-stated items shows text and quote agree, and the owner confirms he reviews learning PRs. It rises to blocking if any owner-stated item turns out to be one he did not say.
- **F3 drops if:** CI goes green and branch protection is on, or the lock gets a date.
- **F5 flips either way on CB-109:** a pre-registered ship verdict on 8 or more paired tasks justifies the tax; not-proven or revert means cutting the size-2 ritual to boot, ledger, gate and close.
- **The whole read is weaker than it looks if:** cloud sessions in practice reuse one brain branch, or push straight to `main` (item 1 shows a session can fast-forward `main`). Then the PR flood and the conflicts in F1 do not arise in that form.
