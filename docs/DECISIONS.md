# Decisions made while building the brain

Each of these was decided without asking you, so the build could proceed. To reverse one, say so in chat or write `OVERTURNED:` under the row. Evidence is in `docs/research/`.

| # | Decision | Why | What you would see if reversed |
|---|---|---|---|
| D-01 | The required core is one short `CLAUDE.md`, skills, agents and plain scripts. Hooks, connectors and plugins are optional extras. | In a chat with two repositories, Claude Code does not load a repository's hooks, connector definitions or plugins (official documentation; confirmed in this session). A brain that depended on them would silently not work. | Nothing would work in two-repo chats unless the cloud environment was set up by hand first. |
| D-02 | "Quantum logic" is delivered as one classical simulated-annealing step in the scheduler, labelled quantum-inspired. Everything else uses the method that measured best. | No quantum hardware is reachable. Measured: greedy packing reaches 99.1% of optimum; annealing helps scheduling (0–2.3% above the best possible against 4–7.5%). | More code labelled "quantum" that performs the same or worse. |
| D-03 | "Machine learning systems" is a file-based learning loop plus Thompson sampling for model and effort routing. | Model weights cannot be trained from a repository. | No change is possible here; this is a limit of the platform. |
| D-04 | At most four helpers at once by default; six agent archetypes instead of a large standing team. | Your history: 20 parallel agents hit the rate limit and produced nothing; ten exhausted the usage window at least twice in two days. Multi-agent runs use about 15 times the tokens of one conversation. | Faster wall-clock on truly independent work, at several times the token use and a real risk of hitting limits. Say "use more helpers" on a specific task to raise it. |
| D-05 | Opus 5.5 at medium effort is the default lead; Fable 5.2 is used for the hard parts. | Anthropic's figures: 93.1% solved at $0.22 per task against 96.3% at $1.39. | Higher cost per task for about three points on the hardest work. You choose the model when you start a chat. |
| D-06 | Memory search uses built-in full-text search, with no vector search. | Within four points of the heavier setup on the one test set available, 1,000 times faster, and needs no downloads at session start. | Slower session starts and installs; possibly better recall once memory is large. Queued as an experiment. |
| D-07 | All project state lives in the project's `.brain/` folder; the brain holds no project names or content. | With many projects, a shared "company repo" would mix their state. Privacy between projects. | The brain would grow with every project and leak one project's facts into another. |
| D-08 | The learned zone is not locked yet. It locks at tag `brain-v1.0.0`, after the live checks in Phase B. | Locking before the pipeline has run on real sessions would block fixing it. | Locking now: any fix to seeded memory would need your override label. |
| D-09 | No board, HR catalogue, payroll simulation or 500-idea table. One adversarial reviewer at the risk levels that need it. | In the earlier project these were built and never used, and their text was paid for in every session. | More ceremony and more always-loaded text. |
| D-10 | The Travel Journal repositories were not touched and are not moved onto the brain. | You said to leave that repo alone in this chat. | Say "adopt the Travel Journal" in a chat with it attached. |
| D-11 | Your standing instructions are stored as instructions, without personal details (no names of people, trips or equipment). The research memo about your past chats is stored without project names or quotes. | They are needed in every project; personal details are not. | Nothing useful; more private data in a repository. |
| D-12 | Learning changes reach `main` as pull requests that you merge. Automatic merging on green is available once GitHub's checks run and one setting is ticked (items 4 and 7 in `NEEDS_YOU.md`). | Keeps a one-click undo for every change, and nothing is promised that GitHub cannot do yet. | Lessons would merge without your click. |
| D-13 | **Your call, 2026-11-10:** the brain has an HR department after all (this reverses the HR part of D-09). It is built lean: 100 agent templates kept as data in a rack that is never always-loaded; one script picks the template, the model and effort, and a token wage, and writes the helper's brief to a file; real token use is settled against the wage from the ledger. | You asked for it. The earlier project's HR was never used because nothing ran it automatically and its catalogue was loaded as text; this one is a script on the hiring path and learns from settled results. | Without it, helpers get hand-written briefs and no wage; nothing learns which kind of agent suits which task. |
| D-14 | **Your call, 2026-11-11:** work runs to completion without stopping to ask or to report; it stops only when you say so or when everything left waits on you. This overturns the plan's cap of three automatic continuations. One exception stays: a step that cannot be undone (deleting data, spending money, publishing to other people, rewriting shared history) waits for your yes in `NEEDS_YOU.md` while the rest goes on. | You asked for it, in those words. The exception keeps the platform's rule for irreversible actions, which the red team found missing from the always-loaded text. | Sessions would stop every few items, or would take irreversible steps without asking. |
| D-15 | `brain hr hire` writes a plain brief by default and suggests the closest templates; one is used only when the lead names it. This narrows D-13: HR still picks the agent, model, effort and wage. | The first pre-registered comparison (8 paired tasks) found briefs with automatically chosen templates passed 6 of 8 against 8 of 8 and used 80% more tokens: the chosen template was the wrong kind of helper on 7 of 8. | Helpers would keep getting method lines for a different kind of work. |
| D-16 | **Your call, 2026-11-11:** Parkinson's law is applied to time as one algorithm (`engine/timebox.py`): every time budget gets a target (median of recent runs) and a stop (their 90th percentile times a safety factor); a run that hits the stop doubles the next one; no learned budget exceeds the old fixed value. Shell commands keep their old timeout until 5 successful runs, then get 3x their 90th percentile with a 2-minute floor, because killing a healthy build costs a whole re-run. Eval graders and the checkpoint lease are left fixed. | A generous fixed allowance is spent in full by a hung step or by work that expands into it; evidence-based budgets end that, and the back-off and cap keep a wrong guess cheap. Graders: a tight limit could fail a valid trial and bias a measurement. Lease: it guards against two writers, so shortening it trades safety, not effort. | Commands, deploy checks and radar requests would wait their old fixed times again, and boot, plans and helper briefs would carry no timebox. |
